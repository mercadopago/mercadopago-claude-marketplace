# Guide: Marketplace — Split Payments 1:1
# Updated: 2026-08-21 | Sources: official Mercado Pago Split Payments and OAuth docs

## Choose the checkout contract first

Marketplace is not a standalone payment API. It adds seller OAuth and a platform
commission to one supported checkout. Resolve `marketplace-checkout=` before
writing code and never mix these contracts:

| Contract | Payment endpoint | Commission field | Buyer UI |
|---|---|---|---|
| `checkout-pro` | exactly `/checkout/preferences` | `marketplace_fee` | Redirect to returned `init_point` |
| `checkout-api` | `/v1/payments` | `application_fee` | Secure MercadoPago.js CardForm or Card Payment Brick |
| `bricks-wallet` | exactly `/checkout/preferences` | `marketplace_fee` | Wallet Brick with `marketplace: true` and dynamic `preferenceId` |

The official Split Payments 1:1 documentation currently describes Checkout Pro,
Checkout API/Transparente through Payments API, and Checkout Bricks. Do not force
the standalone Checkout API Orders contract onto Marketplace.

## Non-negotiable OAuth contract

1. Create a dedicated seller-connection page and preserve the application's
   existing navigation conventions. Mark its root with
   `data-mp-marketplace-page="{contract}"` and its single connection CTA with
   `data-mp-marketplace-connect="oauth"`.
2. Generate a cryptographically random, one-time OAuth `state` on the server,
   bind it to the current authenticated marketplace user/session, persist it in
   the application's durable shared store with a short expiry, and consume it
   exactly once in the callback. An in-memory object or `Map` is not sufficient:
   it fails after restart and across multiple instances. Never accept a state
   generated by the browser and never use a constant.
3. Build the authorization URL with `client_id`, `response_type=code`,
   `platform_id=mp`, the exact configured `MP_OAUTH_REDIRECT_URI`, and encoded
   `state`. The redirect URI must exactly match the Developer Dashboard value.
4. In the callback, handle provider `error`, reject missing/invalid/expired state,
   require `code`, and exchange it server-side at exactly `/oauth/token` using
   `application/x-www-form-urlencoded`, `grant_type=authorization_code`,
   `MP_APP_ID`, `MP_CLIENT_SECRET`, the code, and the same redirect URI.
5. Persist the returned seller `user_id`, `access_token`, `refresh_token`,
   `expires_in`, scopes, and calculated expiry through the application's real
   repository/database. Encrypt access and refresh tokens at rest with an
   application-managed key. Never put seller tokens in cookies, browser storage,
   URLs, HTML, API responses, source files, or logs.
6. Implement refresh through the same `/oauth/token` endpoint with
   `grant_type=refresh_token`. Replace both returned tokens atomically because a
   refresh may rotate the refresh token. Refresh before expiry; if refresh fails,
   mark the connection for reauthorization instead of silently using a platform
   token.
7. Never create a fake seller record or silently fall back to the marketplace's
   own `MP_ACCESS_TOKEN`. Every split request must use the connected seller's
   decrypted OAuth access token in `Authorization: Bearer ...`.

## Trusted commerce contract

- Resolve the seller from an authenticated marketplace relationship attached to
  the trusted cart/order/offer. Never accept `seller_id`, `collector_id`, or an
  OAuth token from the buyer request.
- Resolve items, amount, currency, and commission from trusted server-side state.
  Prefer an opaque cart/order/purchase ID. If an application has no server cart,
  the browser may bootstrap one using only product IDs and quantities; the server
  must resolve titles/prices from its own catalog before creating an immutable
  purchase snapshot. Never accept browser prices, totals, items with prices, or
  commission fields.
- Validate the commission as finite, non-negative, and strictly below the trusted
  purchase total. Apply the marketplace's configured commercial rule on the
  server; never accept `fee`, `application_fee`, or `marketplace_fee` from the
  browser.
- Persist a unique `external_reference` and prevent duplicate submissions. Send
  `X-Idempotency-Key` on Payments API creation.
- Do not add `collector_id` to the payment payload. OAuth's returned `user_id`
  identifies the connected seller, while the seller OAuth access token in the
  Authorization header determines the receiving account.
- Handle loading, processing, success, pending, and actionable error states. Do
  not expose raw Mercado Pago responses or secrets to the buyer.

## Contract: `checkout-pro`

- Use the seller OAuth access token on the backend.
- Create exactly `/checkout/preferences` with trusted `items`,
  `marketplace_fee`, `external_reference`, and production-safe back URLs.
- Never add a `v1` segment to the Preferences path.
- Return only the fields the client needs (`preferenceId`, `initPoint`) and
  redirect only to `init_point`.
- Reuse the application's real checkout CTA, mark it
  `data-mp-marketplace-checkout="checkout-pro"`, and remove the old competing
  handler. Do not create a local card form.

## Contract: `checkout-api`

- Use the integrator/platform public key in the frontend and the connected
  seller OAuth access token in the backend.
- Create through `/v1/payments` with trusted `transaction_amount`, secure
  single-use `token`, `installments`, `payment_method_id`, payer data,
  `application_fee`, and `external_reference`.
- Tokenize with MercadoPago.js CardForm or the official Card Payment Brick. Never
  render a manual token input and never collect raw card fields.
- For CardForm, preserve visible persistent labels and all required lifecycle
  selects (`issuer`, `installments`, `identificationType`) hidden but not
  disabled. Deliver the public key through the application's public runtime
  configuration; a vanilla server endpoint must be JSON + `no-store`.
- Create a dedicated checkout screen and link the resolved entry CTA to it. Mark
  the screen `data-mp-marketplace-checkout="checkout-api"`.

## Contract: `bricks-wallet`

- Use the integrator/platform public key in the frontend and the seller OAuth
  access token in the backend.
- Create a fresh preference server-side for the trusted purchase at exactly
  `/checkout/preferences`, including `marketplace_fee` and
  `external_reference`.
- Initialize the Wallet Brick with the returned dynamic `preferenceId` and
  `marketplace: true`. Never hardcode a preference ID or trust browser prices.
- Mark the dedicated Brick page
  `data-mp-marketplace-checkout="bricks-wallet"` and link the application's real
  checkout CTA to it.

## Required environment contract

```dotenv
MP_APP_ID=
MP_CLIENT_SECRET=
MP_OAUTH_REDIRECT_URI=https://your-marketplace.example.com/oauth/mercadopago/callback
MP_TOKEN_ENCRYPTION_KEY=
MP_PUBLIC_KEY=
APP_URL=https://your-marketplace.example.com
```

`MP_CLIENT_SECRET`, seller OAuth tokens, refresh tokens, and the encryption key
are server-only. `MP_PUBLIC_KEY` is public. Do not inject secrets into HTML.

## Acceptance check

After writing OAuth, persistence, the selected checkout, and both seller/buyer
CTAs, run from the target project root:

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/validate-marketplace-integration.mjs" . "{contract}"
```

Fix every failure before reporting success. A mocked OAuth callback is suitable
for automated UI/runtime smoke tests. A real OAuth authorization remains an
explicit test step because it requires seller consent and valid app credentials.
